## 1. 任务概述

### 需求来源

- [订单退款 Spec](../../requirements/order-refund.md)
- [站内钱包全额退款设计草案](../../design/order-refund-wallet-design.md)

### 本次目标

钱包支付订单的全额退款继续异步受理。首次申请返回 `pending`。正金额退款成功时，从商家钱包扣除原订单实付金额并等额退回买家，记录可按退款 ID 追溯的资金流水。重复申请和后台重复执行只产生一组资金变动和流水。零元退款以退款记录留痕。

### 非目标

部分退款、接入真实外部支付渠道、通用钱包转账、处理历史模拟退款记录及任务、退货收货与入库。

[商家同意退款操作](../../requirements/order-refund.md#商家同意退款)留作后续任务。它用于需要商家核实履约情况的退款申请，例如确认商品是否已发出、退回的商品是否已收到。本期仍由后台自动处理已受理的退款。哪些申请需要商家同意、同意后何时启动退款，由后续需求确定。

## 2. 技术实施方案（Plan）

### 当前实现

退款接口受理后写入退款和任务记录。模拟渠道成功时，现有 Worker 更新退款和订单状态，并按条件返还优惠券。这笔订单的买家扣款和商家入账目前只发生在支付流程。

### 实施方案草案

1. 保留现有申请和查询入口，复用退款任务表、扫描和退券流程。新申请创建站内退款任务，后台直接执行钱包退款。既有模拟任务保留原有处理路径，历史记录按本期范围暂缓处理。
2. 后台在同一数据库事务内锁定退款记录，重新确认退款尚未结束、任务仍可执行，再锁定订单并校验已支付状态。正金额退款按现有支付的买家、商家顺序锁定钱包，再有条件地扣减商家并增加买家余额。两条流水、余额、退券、退款和订单状态以及任务完成一起提交，失败时整体回滚。零元退款走相同的状态与退券流程，跳过钱包更新和流水写入。
3. 正金额退款复用 `wallet_logs`。两条记录用现有 `order:` 保留命名空间，按退款 ID 和扣减、入账方向生成不同幂等键。退款行锁和终态检查拦截重复执行，流水的唯一键作为额外约束。
4. 区分内部失败原因与买家可见信息。合法申请先返回受理状态。退款进入 `failed` 时，订单详情的 `refund.failure_reason` 统一返回「本次退款未完成」，时间线使用可公开的信息。

### 测试变化

- 先为新申请补充钱包余额和流水的失败用例。现有受理测试断言任务类型是 `create_refund`，新任务类型属于有意变更，方案获批后更新这一断言。
- 使用显式模拟任务覆盖现有渠道重试和查询场景，保留这些场景的原有行为断言。
- 补充零元退款、并发处理同一退款、资金写入失败回滚以及订单详情隐藏内部失败原因的验证。

### 影响范围

- 订单退款 Worker、钱包资金更新、退款与订单状态，以及现有退券流程。已支付订单退款成功后不返还库存，未支付订单超时关单时仍返还库存。
- 退款申请与查询的 HTTP 契约，包含首次受理、重复申请和后台失败后的可观察结果。
- 退款集成测试、支付与钱包相关回归。数据迁移和错误码变更待规则及方案评审。

### 风险与待确认问题

- 商家余额不足时，建议后台沿用现有退避策略，最多尝试 5 次，耗尽后标记 `failed`。期间余额和订单状态保持原值，对买家只显示通用进度和结果。
