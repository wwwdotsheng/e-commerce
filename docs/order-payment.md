# 订单余额支付

买家调用 `POST /api/v1/order/:id/pay`，用自己在 `user_wallets` 中的余额支付待支付订单。支付成功时，订单金额立即从买家余额扣除并记入商家余额，不经过平台结算账户。

## 一次支付事务

1. 以 `SELECT ... FOR UPDATE` 锁定订单行，并限定 `user_id` 为当前登录买家。
2. 校验订单状态与支付截止时间。
3. 扣减买家余额：`UPDATE ... WHERE user_id = ? AND balance >= ?`，余额不足时返回 `A03102`。
4. 把同一金额加进商家余额。
5. 订单状态改为 `4`（已支付）并写入 `paid_at`。

余额、两条钱包流水和订单状态在同一个数据库事务里提交，任意一步失败全部回滚，不会出现“钱扣了但订单没变”的中间状态。

## 幂等与重复请求

- 同一订单再次支付时直接返回当前订单，不再扣款、不再入账。订单行锁保证并发请求串行判断状态。
- 钱包流水使用订单 ID 派生的唯一幂等键：买家扣款 `order:<id>:payment`，商家入账 `order:<id>:income`；即使上层判断被绕过，`wallet_logs.idempotency_key` 唯一索引也会拒绝第二条流水。
- 支付接口不需要额外幂等键，订单 ID 本身就是幂等键。
- `order:` 是系统流水的保留命名空间：充值的幂等键由用户提供，因此 `POST /wallet/deposit` 会拒绝空键、超过 64 字符、含字母/数字/`.`/`_`/`:`/`-` 之外字符、或以 `order:` 开头的键（`A03103`），避免用户预占订单流水键、导致该订单之后永远无法支付。
- 如果历史数据里已有充值键占用了 `order:` 命名空间，支付写入买家扣款流水时会命中唯一索引；这时返回 `A05104 订单支付流水冲突`，不再退化为 `B01001`，需要人工清理冲突流水后才能支付。

## 拒绝支付的情况

| 情况 | 返回码 |
|---|---|
| 订单不存在，或不属于当前买家 | `A00002` |
| 买家余额不足 | `A03102` |
| 订单已取消、已超时或已完成 | `A05102` |
| 已过 `payment_deadline`，超时消息尚未处理 | `A05103` |
| 历史充值键占用了订单流水键（数据冲突） | `A05104` |

超过截止时间但还没被超时消息关闭的订单也拒绝支付，避免“先关闭释放库存、又收款”的竞态。关闭订单由现有超时流程负责。

## 与超时关闭的关系

支付和超时关闭都会先锁定同一订单行：

- 支付先提交：超时消息随后发现状态不是“处理中”，不会重复释放库存、归还优惠券，也不会覆盖 `paid_at`。
- 超时先提交：支付看到已超时状态，返回 `A05102`，余额不变。

## 金额与状态

- 支付金额使用下单时保存的 `payable_amount`，不重新读取商品价格。优惠券把应付金额抵扣到 0 时，零元订单直接转为已支付，不产生资金流水。
- 订单状态：`0` 处理中（待支付）、`1` 已完成（履约，尚未接入）、`2` 已取消、`3` 超时、`4` 已支付。
- `paid_at` 只在支付成功时写入；历史订单不会被补写。
